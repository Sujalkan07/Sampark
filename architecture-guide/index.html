Sampark: Full-Stack C++ Chat Application

A comprehensive, code-verified technical architectural guide detailing the communication mechanics, internal concurrency models, SQLite WAL persistence, OpenSSL cryptography, and end-to-end message delivery flow.

SECTION 01

Project Overview

Sampark is a full-stack, high-performance direct messaging and group communication application. Unlike conventional enterprise chat systems built on heavyweight interpreted runtimes or third-party cloud services, Sampark is engineered from fundamental principles: a custom C++20 backend HTTP server, an embedded SQLite3 database operating in Write-Ahead Logging (WAL) mode, and a modern React 18 single-page frontend styled with Tailwind CSS.

⚡
High Performance & Low Footprint
Compiled C++20 backend using cpp-httplib with multithreaded socket pooling. Native speed, tiny memory usage, and zero cloud lock-in.
🔒
Rigorous Cryptography
OpenSSL PBKDF2-HMAC-SHA256 with 100,000 iterations, 16-byte cryptographically secure random salt, and constant-time hash verification against timing attacks.
🛡️
Thread-Safe Persistence
SQLite3 WAL mode enabled. Multi-threaded worker thread access synchronized via RAII std::lock_guard<std::mutex> and parameterized statement bindings.
🔄
Incremental Delta Polling
Client-side 2.5s polling loop querying ?after={latestMessageId} to retrieve new messages with zero stateful zombie-socket leaks.
Verified Core Capabilities from Codebase
  • User Authentication: Secure sign-up, login, session validation (168h TTL), password change with active session revocation.
  • Direct Messaging: Normalized 1-on-1 chats with automatic participant sorting (user_low_id, user_high_id).
  • Group Conversations: Role-based access control (admins vs members), member additions, role promotions, and group exit.
  • Message Lifecycle: Rich text messages, soft deletion (is_deleted = 1), editing with timestamp tracking, quote replies.
  • Reactions & Emoji: Deduplicated emoji reactions tracked per user and message ID.
  • Attachment Sniffing: Strict 10MB upload limit with binary magic-byte inspection (PNG, JPEG, GIF, WebP, PDF, DOCX, DOC, TXT).
  • User Preferences & Presence: Light/dark theme preferences, sound alerts, read receipts, and real-time activity timestamps.

SECTION 03

Complete Message-Sending Workflow

The following numbered sequence traces the end-to-end journey of a single message from the moment User A hits "Send" until User B hears the notification chime and views the message on screen.

FIGURE 3.1: END-TO-END MESSAGE LIFECYCLE (NUMBERED PRESENTATION PATH)
  1. Stage 1: DOM Event Capture & Optimistic Preparation
    In ChatPanel.jsx, User A submits a message. React's handleSend() trims whitespace, verifies the body does not exceed 4000 characters, creates a temporary message object in component state, and invokes api.sendMessage(conversationId, { body, replyToId, attachmentId }).
  2. Stage 2: Network Transport via Reverse Proxy
    The browser executes an HTTP POST via fetch() targeting /api/conversations/:id/messages. The Vite development server reverse-proxies this socket from port :5173 to the native C++ backend on port :8080.
  3. Stage 3: Server Routing & Session Authentication
    Server.cpp executes pre-routing CORS origin checks. The request enters MessagingController::handleSendMessage(). The session cookie is extracted and checked against the SQLite sessions table using AuthService::authenticate(). If the session is missing or expired, a 401 Unauthorized is returned immediately.
  4. Stage 4: Business Rules & RBAC Validation
    MessagingService::sendMessage() verifies that the conversation exists and executes convRepo_->isParticipant(). If User A is not in the conversation, the request is halted with 403 Forbidden. If a replyToId is supplied, it confirms that the referenced message belongs to the exact same conversation.
  5. Stage 5: Thread-Safe SQLite WAL Persistence
    SqliteMessageRepository::createMessage() acquires an RAII std::lock_guard<std::mutex>. It constructs an RAII prepared Statement, binds parameters, and calls sqlite3_step(). SQLite writes the record to the Write-Ahead Log file (connectx.db-wal) and updates the conversation's updated_at timestamp.
  6. Stage 6: Sender HTTP 201 Acknowledgment
    The C++ server returns HTTP 201 Created with the serialized ChatMessage JSON payload. User A's client reconciles the optimistic temporary message with the permanent database ID.
  7. Stage 7: Recipient Polling Discovery
    User B's client runs an active setInterval(poll, 2500). It executes GET /api/conversations/:id/messages?after={latestMessageId}. The C++ server queries SQLite for rows with id > afterId, returning only the newly created message delta.
  8. Stage 8: DOM Insertion, Audio Notification & Read Receipt
    User B's React component checks for existing IDs to guarantee deduplication, appends the new message to the active thread, triggers an audio notification chime via Web Audio API, and automatically dispatches a POST /api/conversations/:id/read sync request to update read timestamps.

SECTION 06

Networking, Sockets, and HTTP Transport

Sampark utilizes standardized HTTP/1.1 over TCP sockets. This architecture was chosen deliberately over raw WebSockets or proprietary binary protocols for multiple engineering reasons:

1. Stateless Resilience
Long-lived WebSockets frequently drop across mobile networks, firewalls, and sleep states. HTTP REST primitives guarantee idempotent retries without zombie connection leaks.
2. Incremental Delta Polling
Clients query /api/conversations/:id/messages?after={latestId} every 2500ms. SQLite indexed queries on (conversation_id, id) execute in sub-millisecond time.
3. Strict Buffer Sizing
The C++ server sets svr_.set_payload_max_length(15 * 1024 * 1024). Requests exceeding 15MB are aborted at socket level before memory buffering occurs.
SECTION 07

Concurrency, Threading, and Mutex Protection

The backend concurrency model operates as a multi-threaded server backed by a single-threaded write serialized SQLite database.

FIGURE 7.1: CONCURRENCY MODEL & RAII MUTEX SYNCHRONIZATION

RAII Mutex Idiom: Every repository operation constructs a std::lock_guard<std::mutex> lock(db_.getMutex()) at the top of the function. This guarantees that even if a SQL statement throws an exception or returns early, the mutex is automatically released when the lock object goes out of scope, preventing deadlocks.

Error Handling, Input Sanitization & Edge Cases

The server implements defensive validation at every stage, rejecting malformed, malicious, or unauthorized requests with precise HTTP status codes:

Status Code Trigger Condition Detecting Component Application Response & Cleanup
400 Bad Request Empty message body without attachment; body > 4000 characters; invalid reply ID; directory traversal (..) in filename. Validator.cpp Rejects request before database touch. Returns descriptive JSON error message.
401 Unauthorized Missing connectx_session cookie; expired token (> 168 hours); non-existent session. AuthService.cpp Halts request immediately. Frontend redirects user to /login.
403 Forbidden Sender is not an active participant of the conversation; non-admin attempting group role change. MessagingService.cpp Access denied. Database transaction aborted.
404 Not Found Target user or conversation ID does not exist in SQLite database. Repository layers Returns 404 JSON response.
413 Payload Too Large Incoming HTTP raw body exceeds 15MB socket buffer limit. httplib::Server Socket connection closed immediately before memory allocation.

"Good morning, Professor. Today I am presenting Sampark, a full-stack, high-concurrency messaging application engineered in modern C++20 and React. Rather than relying on external cloud backends, Sampark executes locally on a lightweight native C++ daemon running cpp-httplib with multithreaded socket pools.

For persistence, we utilize embedded SQLite operating in Write-Ahead Logging (WAL) mode. Because multiple HTTP worker threads can handle requests simultaneously, our repository layer wraps database transactions in RAII std::lock_guard<std::mutex> primitives, preventing race conditions.

Security is built directly into the core: user passwords are protected with OpenSSL PBKDF2-HMAC-SHA256 across 100,000 rounds with a 16-byte random salt, and attachments undergo binary magic-byte inspection to prevent spoofed uploads.

When a user sends a message, it is validated, atomically inserted into SQLite, and acknowledged with an HTTP 201 response. The recipient client runs a 2.5-second incremental delta polling loop querying ?after={latestId}, updating the React DOM, playing an audio chime, and automatically dispatching a read receipt. Thank you, and I welcome any questions regarding our code or design."

Anticipated Professor Questions & Technical Answers

Q1: Why did you choose incremental delta polling over WebSockets?
Answer: While WebSockets offer persistent full-duplex sockets, they introduce stateful connection management complexity, ghost connection leaks during mobile network handoffs, and sticky-session load balancing requirements. Our 2.5-second cursor polling (?after={latestMessageId}) is completely stateless, immune to dropped socket accumulation, and executes SQLite B-Tree range queries in less than 0.5 milliseconds using indexes on (conversation_id, id).
Q2: How do you guarantee thread safety with multiple concurrent worker threads accessing SQLite?
Answer: SQLite handles are protected at two levels: First, we enable SQLite WAL mode (PRAGMA journal_mode = WAL;), which allows multiple simultaneous readers without blocking writers. Second, inside our C++ Database class, we maintain a std::mutex mutex_. Every repository write operation acquires a std::lock_guard<std::mutex>, serializing critical write statements and guaranteeing zero race conditions across worker threads.
Q3: How does your application protect against file upload attacks and disguised malware?
Answer: Rather than blindly trusting the MIME type header sent by the client, our C++ Validator::validateAttachment() performs binary magic-byte sniffing on the raw payload buffer. We check the actual byte signatures—such as \x89PNG\r\n\x1a\n for PNG and 0xFF 0xD8 0xFF for JPEG. Furthermore, we sanitize filenames to eliminate directory traversal characters (.. and path separators) and enforce a hard 10MB ceiling.
Q4: How are passwords stored and authenticated against timing attacks?
Answer: We generate a 16-byte cryptographically secure random salt per user using OpenSSL's RAND_bytes(). We hash the password using PKCS5_PBKDF2_HMAC with EVP_sha256() over 100,000 iterations to produce a 256-bit key. During login verification, we compare the calculated hash using OpenSSL's CRYPTO_memcmp(), which executes in constant time to prevent timing side-channel attacks.
